# Compiler dependency and source-boundary audit

## Boundary

The one executable compiler seed is the 2,544-byte i386 qfitzah image pinned
by `seed.sha256`. Building that seed with GNU binutils is outside this boundary;
the complete bootstrap recipe accepts the already trusted image and checks its
hash. It does not invoke Nix or a host compiler/assembler/linker/archiver.
The host must run both i386 and amd64 Linux executables and provide `/proc`.

Host Bash/POSIX shell, Git, tar, patch, coreutils, grep and comparison/hash tools
perform orchestration, source export or validation. Execution tracing and
monitoring are observation tools, not compiler inputs. Public source objects
can be fetched beforehand; generated artifacts cannot be reused in fresh runs.

## No higher-libc prerequisite in the compiler chain

This is not a claim that the build host itself is libc-free. The distinction is
between the compiler/runtime dependency graph and the host orchestration tools.

- qfitzah and its Scheme runtime use their own Linux syscall/assembly support.
- Stage0/M2, Blynn and HCC use pinned **M2libc source** and source-built runtimes,
  not glibc, musl or the GHC runtime. M2's library/header path is explicitly set
  to the exported stage0 M2libc tree.
- The first TinyCC is linked from HCC-generated M1 and the target's source C/M1
  syscall/memory support. Mes headers are source input; a pre-existing Mes libc
  binary is not required to break the initial compiler/library dependency cycle.
- That source-built TinyCC compiles **Mes libc source**, its own `libtcc1.c` and
  `alloca.S`; subsequent native compiler/runtime rebuilds converge. There is no
  host libc archive, startup object, assembler, linker or compiler-runtime input.
- HCC's include search starts with an empty directory list and uses the current
  source directory plus explicit `-I` paths. Those paths select the pinned
  TinyCC/Mes headers. Native finalization also uses `-nostdinc` with private
  include paths. The final installed header tree contains no symlinks to host
  headers; configured library/include paths are relative to the private prefix.

The strengthened post-build audit examined **all 64 retained ELF executables**
(9 i386, 55 amd64), including intermediate tools: none contains `PT_INTERP` or
`PT_DYNAMIC`. This complements source/link-command provenance; static linkage
alone would not prove that a host libc archive had not been imported.

The remaining host shell, Git, tar, patch and file/hash utilities may themselves
use the host libc. They are declared orchestration dependencies, not hidden
compiler/runtime ancestors. Linux is also a platform prerequisite. Eliminating
those host-tool dependencies would be a separate shell/coreutils/kernel
bootstrap, not something this PR claims to have achieved.

## Data and compiler roles

| Input | Treatment |
|---|---|
| qfasm, scheme0, sc1, rsc sources | Rebuilt through the trusted seed; no host Scheme |
| stage0 hex0/kaem annotated machine source | Assembled by the rsc-built hex0 tool; never imported as an executable seed |
| stage0 bootstrap-seeds | Excluded from exports and not required by fetching; earlier binary comparison was only a post-generation oracle |
| stage0/M2 and M2libc sources | Source-built kaem runs the mini/full recipes; all six final tool hashes must match pinned answer data |
| root Blynn `blob/*.source` | Deleted from prepared tree; not compiler inputs |
| high-level `singularity` | Compiled by the small rsc-built SKI compiler; source self-compilation must reproduce its image |
| later Blynn compiler images, native C and executables | Regenerated by the preceding compiler/VM and M2 |
| current Blynn and HCC object IR/C | Regenerated from pinned Haskell source, including the object materializer built through M2 |
| HCC/TinyCC M1 and ELF | HCC emits M1; source-built M1/hex2 assemble and link it |
| GNU Mes | Libc source only; no Mes interpreter, MesCC or Nyacc is run |
| TinyCC runtime and final compiler | Native TCC rebuilds libc, its own libtcc1/alloca, and itself; final compiler and library fixpoints are required |

The stage0 M2libc pin is used throughout; neither of the target's alternative
M2libc revisions is silently substituted. `sources.tsv` records commits and
trees. Exports verify both and disable Git replacement objects. They do not
copy mutable worktrees. Local patches apply to fresh exports or private source
copies; the original checkouts remain unchanged.

## Repairs and validation

The README documents VM buffer safety, exact patch-context repairs, relative
include/source paths, the native numeric converter and strict linker-error
handling. Mes's heap-based `alloca` is excluded from the final native runtime;
TinyCC's assembly allocator is built instead. Duplicate-symbol diagnostics are
not ignored or downgraded. The regression requires nonzero status and no output.

The corrected component build passed ABI, integer/floating arithmetic, decimal
conversion, variable-length arrays, allocation, file I/O, repeated code output,
syntax rejection, linker rejection and native compiler/library fixpoints.
ELF inspection found an amd64 executable without `PT_INTERP`: no host dynamic
loader/libc is needed. Runtime archive timestamps are zero. A relocated copy
also passed the full C/numeric/diagnostic suite using only its own headers and
runtime; the compiler contains no `/tmp/qfitzah`, `/home/siraben` or `/nix/store/`
prefix. This is a limited
bootstrap libc, not a complete ISO/POSIX implementation; see README limitations.

The completed HCC-to-TinyCC component execution trace contained source-built
HCC/M1/hex2/TinyCC and ordinary shell/file utilities, not a host compiler.
The complete fresh run passed in 24m11.371s. Its execution trace and independent
cross-directory output comparison were inspected and passed; see
[ACCEPTANCE.md](ACCEPTANCE.md). Relative entries were matched to the stage0
scripts' source-directory scopes, TinyCC's artifact-directory scope and the
native finalizer's source-directory scope. The optional post-build
`audit-build.py` checks timings, phase completion, seed/recipe/artifact hashes,
ELF/runtime metadata, independent outputs and executable-path categories. It
requires Python only for observation, not compilation. It reports relative
execution paths separately: their working directories must also be reviewed
against the stage0, TinyCC and native-finalizer scripts, not assumed from a
basename match.
